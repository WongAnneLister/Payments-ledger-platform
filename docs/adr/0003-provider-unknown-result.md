# ADR-0003：Provider 未知结果的处理

状态：Accepted（PR00 冻结） · 日期：2026-09-10

## 背景

网络响应与远端执行不是原子事件。以下三种情况在本地**完全无法区分**：

1. 请求根本没发出去。
2. 请求已发出，Stripe 已受理并扣款，但响应在返回途中丢失。
3. 请求已发出，Stripe 拒绝了它，但响应丢失。

把这三者都归类为"失败"会导致：客户已被扣款、本地显示失败、重试造成**第二次真实扣款**。这是支付系统最昂贵的一类 bug。

Stripe 的幂等键可以缓解，但有两个限制（[S2](https://docs.stripe.com/api/idempotent_requests)）：**结果会被缓存（包含部分错误结果）**，且**键不会永久保留**。窗口过期后，同一个键可能被当作全新请求处理。

## 决策

**把"结果确定性"建模为独立维度 `resolution ∈ {KNOWN, UNKNOWN, CONFLICT}`，与业务状态正交。`UNKNOWN` 不等于失败，也不覆盖最后已知的 provider 状态。**

### 核心规则

| # | 规则 |
|---|---|
| R1 | 超时、暂态错误、查询暂空 → `UNKNOWN`，**不**判定为业务失败 |
| R2 | 每个资金写操作使用**持久化的操作级幂等键**；create / confirm / refund **不共用**同一键 |
| R3 | 幂等键存 PostgreSQL，**不依赖 Redis**（缓存过期不得导致重复创建） |
| R4 | 恢复优先级：**查询取证 > 窗口内原键重试 > 升级人工**。永不换键 |
| R5 | 窗口已过 + 无外部 ID + 无法排除已受理 → 保持 `UNKNOWN`，转 `ESCALATED`，告警 |
| R6 | 退款在 `UNKNOWN` 期间**保留预占 H**，不释放额度 |
| R7 | `ProviderEvidence` 在超时与失败时**同样必须持久化**——它可能是唯一的取证锚点 |
| R8 | 过期租约 Worker 的迟到返回**不更新**控制状态，但**必须**另存为 `provider_observation` |

### 决策树

```text
UNKNOWN
  ├─ 有 external_object_id？ ──是──► 权威查询取证 ──► RESOLVED
  ├─ 有持久业务关联可反查？ ──是──► L3 外部枚举取证 ──► RESOLVED / 人工
  ├─ 仍在已验证保留窗口内？ ──是──► 用【原键】安全重试
  └─ 无法排除已受理 ──────────────► ESCALATED
                                     ✗ 不换键 ✗ 不重发 ✗ 不标记失败
```

**"等待够久"不是安全重试的证明。** 时间流逝不产生证据。

### 错误归一化

Provider 端口返回归一化 `classification`，业务层**只依据它决策**，不解析原始错误文案。关键区分：

| 分类 | 远端是否可能有效果 | 处理 |
|---|---|---|
| `DEFINITIVE_REJECT` | **否** | 结束本次尝试（卡拒付只终结 attempt，不终结 Payment） |
| `TIMEOUT_UNKNOWN` | **可能** | 进入 UNKNOWN 决策树 |
| `TRANSIENT_EMPTY` | **未知** | 继续 L1 退避查询，**不**推断未执行 |

**`TIMEOUT_UNKNOWN` 与 `DEFINITIVE_REJECT` 的区分是本项目的核心资金安全边界。**

完整分类表见 [Provider 端口契约 §5](../contracts/provider.md)。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| **超时即判失败，让客户重试** | 直接导致重复扣款。这正是项目要解决的问题。 |
| **超时即判成功（乐观）** | 未扣款却发货，且账本凭空多一笔收入。 |
| **无限用原键重发直到成功** | 掩盖了远端键过期这一真实风险。窗口过后同键会被当作新请求 → 重复扣款（AC-V1-09）。 |
| **换一个新幂等键重试** | 提供方必然当作新请求处理，几乎保证重复扣款。**任何情况下都禁止。** |
| **只依赖 Redis 做幂等** | 缓存过期或清空后业务唯一性即失效。本地唯一键必须持久化。 |
| **用超时时长推断结果** | 时间不是证据。慢响应与丢响应不可区分。 |
| **丢弃过期 Worker 的返回** | 可能丢掉唯一的外部对象 ID，使后续取证失去锚点。 |

## 后果

**正面**

- 重复扣款在设计层面被排除，并可用 Fake 的独立效果计数器证明（`paymentEffectCount` / `refundEffectCount`）。
- UNKNOWN 可见、可告警、可人工介入，不会静默积压。
- 支付与退款共用同一套恢复模型，无需两份实现。

**负面与缓解**

| 负面 | 缓解 |
|---|---|
| 部分订单会长期停在 UNKNOWN | L1/L2/L3 三层收敛 + 年龄阈值告警 + 人工调查任务 |
| 退款额度被 UNKNOWN 预占长期占用 | 夜间"退款预占老化"检查；失联预占无告警判 `FAIL` |
| 用户体验上"既不成功也不失败" | 结果页明确引导**查询**而非重复支付（AC-V1-32） |
| 需要可控时钟与有限窗口的 Fake | PR04 必须实现有限保留窗口，不能永久神奇去重 |
