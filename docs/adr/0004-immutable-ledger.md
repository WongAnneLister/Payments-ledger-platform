# ADR-0004：不可变账本与一次性受控过账

状态：Accepted（PR00 冻结） · 日期：2026-09-10

## 背景

账本要回答"钱怎么变化、每条来自哪个外部资金变动或内部决策"。如果凭证可以被修改，任何历史答案都不可信：一次 `UPDATE` 就能让昨天的对账结论失效，且没有痕迹。

同时存在一个具体攻击面：**即使借贷仍然平衡，向已封存凭证追加一对相等的借贷分录，也会悄悄扩大这张凭证。** 只禁止 `UPDATE`/`DELETE` 是不够的。

## 决策

**`POSTED` 是唯一的、最终的、封存的 Journal 状态。凭证在一次受控写入中构建完成并校验，提交后不可改、不可删、不可追加 Entry。**

### 过账流程

```text
单个数据库事务内：
  1. 按固定锁序取得必要控制行 / 账户行（见 ADR-0007）
  2. 唯一 financial_event 插入（scope + event_key 唯一）
  3. 受控一次性写入 journal + 全部 journal_entry
  4. 校验最终分录集合（延迟约束触发器）
  5. 更新 balance_projection
  6. 需要时写 Outbox
  7. 提交
```

**"受控构建"与"封存"如何兼容**：分录集合在**应用内存中**构建完成后，在同一事务内一次性写入；`journal` 表**没有**草稿状态，也没有外部可修改的已提交草稿。校验使用 **PostgreSQL 延迟约束触发器**（`CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`），在**提交时**检查最终集合，因此不存在"先写一行、后补一行"的中间可见窗口。

### 强制的数据库约束

| 约束 | 内容 |
|---|---|
| 平衡 | 同币种 `sum(debit) = sum(credit)`，提交时校验 |
| 最小行数 | 至少两条有效分录；拒绝空凭证与单行凭证 |
| 金额有效 | 每条 Entry 金额 > 0；不产生零额分录 |
| 事件唯一 | `UNIQUE (organization_id, environment_id, event_key)` |
| 一对一 | `UNIQUE (financial_event_id)` on `journal` |
| 范围一致 | 复合 FK 强制 Entry 与 Journal 与 Account 的 org/env/currency 一致 |
| 不可变 | 应用运行角色对 `journal` / `journal_entry` **只有 INSERT**，无 UPDATE / DELETE |
| **禁止追加** | 封存后**禁止**向已有 Journal 插入任何 Entry，**即使新增的是一对借贷相等的分录** |

"禁止追加"由 Journal 上的 `sealed_at` 标记 + Entry 插入触发器共同实现：Entry 只能在其 Journal 尚未封存的同一事务内写入。

### 修正方式

**一律追加关联的新凭证**：

| 场景 | 处理 |
|---|---|
| 记错了 | 新 `financial_event` + 新 Journal（reversal），通过 `reversal_of_journal_id` 关联 |
| 外部事实变化 | 作为**新事实**入账（如退款失败返还 BT） |
| 人工调整 | 经独立审批后追加 adjustment Journal |

**唯一键不能通过换随机 ID 绕过。** 重复冲正命令必须幂等。

### 投影写入口

`balance_projection` **只**由 `LedgerPostingService` 在过账事务内更新。BT Importer、Webhook 处理器、分润服务、争议服务调用过账服务之后，**不得再次累加**任何余额。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| **允许 UPDATE 修正凭证** | 历史结论不可复算；审计链断裂；无法回答"当时账上是什么"。 |
| **草稿 Journal + 后续封存** | 产生外部可修改的已提交草稿窗口。并发入口可能在此窗口插入分录。PR00 明确要求"不存在外部可修改的已提交草稿 Journal"。 |
| **只禁 UPDATE/DELETE，允许追加平衡的 Entry** | 正是本 ADR 要堵的漏洞：平衡不等于不可变，追加一对相等分录可悄悄扩大旧凭证（验收 §3.1 第 4 条）。 |
| **仅用 Java 断言保证平衡** | 绕过服务直接 SQL 写入即失效。PRD 要求约束在数据库实现，并用**实际应用角色**验证。 |
| **软删除（`deleted_at`）** | 等价于可变；重建结果依赖"当前是否被标删"，不可复算。 |
| **每次入账后由导入器再同步一次余额** | 同一 BT 经 Webhook / Importer / 恢复器多入口进入时，余额会被加多次（验收 §3.1 第 7 条）。 |
| **事件溯源（只存事件，余额全靠回放）** | 每次查询都要回放，性能与运营页面不可用；且仍需投影，问题没消失。本决策保留投影但限定唯一写入口。 |

## 后果

**正面**

- 任何历史时点的余额都可由不可变分录独立重建，这是 I-07 与夜间检查的基础。
- 独立重建器可以绕开生产投影路径，从而**发现投影漂移**（验收 §7.1 的第二种"独立"）。
- 审计链完整：每张凭证都能追到来源财务事件与外部证据。

**负面与缓解**

| 负面 | 缓解 |
|---|---|
| 更正操作产生更多凭证 | 这是特性不是缺陷；`reversal_of_journal_id` 提供可读关联链 |
| 无法"就地修 typo" | 描述性字段放在 `financial_event` 或独立注释表，不在已封存 Entry 上 |
| 延迟约束触发器有性能开销 | 仅在提交时执行一次；PR20 性能实验记录实际影响 |
| 投影与分录可能漂移 | 夜间独立重建 + 故意改错投影的 fixture 必须能检出残差 |
