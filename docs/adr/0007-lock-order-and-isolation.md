# ADR-0007：锁顺序与隔离级别

状态：Accepted（PR00 冻结） · 日期：2026-09-10

> **这是 PR00 必须做出的两个强制决策之一。**

## 背景

多个不变量需要锁定稳定的父记录/控制行：

- I-03 退款额度：锁 `payment` 控制行才能保证 `0<=R+H<=C`
- I-04 分润上限：退款预占与分润调整必须在同一事务
- I-06 出款守恒：锁 payout 分配控制行与银行行
- I-01/I-07：账本入账要锁相关科目行

不同入口（API 退款、Webhook 处理、BT 导入、争议处理、银行匹配、对账重跑）会以不同顺序触碰这些行。**只要两个入口的加锁顺序相反，就必然产生死锁。**

## 决策

**全局固定锁序，按 rank 升序获取；同 rank 内按主键升序。**

| rank | 对象 | 说明 |
|---|---|---|
| 10 | `business_order` | |
| 20 | `payment`（支付控制行） | 退款/分润/争议的共同父行 |
| 30 | `refund_control` | |
| 40 | `dispute`（争议控制行） | |
| 50 | `share_allocation` | |
| 60 | `payout`（分配控制行） | |
| 65 | `bank_statement_line` | |
| 70 | `financial_event` | |
| 80 | `ledger_account` | 多账户按 `ledger_account_id` **升序** |
| 85 | `balance_projection` | 同上，按稳定 ID 升序 |
| 90 | `outbox_event` | 仅 INSERT |

### 五条规则

1. **只能按 rank 升序获取**；同 rank 内按主键升序（UUID 字节序，稳定且与插入顺序无关）。
2. **纯账本业务可以跳过前面的业务锁**（例如只做一次内部重分类，直接从 rank 70 开始）。
3. **拿到账本锁（rank ≥ 70）之后，绝不能反向索取业务锁（rank ≤ 60）。** 这是最容易被违反的一条——BT 导入器在入账过程中发现需要更新退款状态时，必须**重新开始整个事务**，而不是就地回头加锁。
4. **隔离级别 `READ COMMITTED` + 显式 `SELECT ... FOR UPDATE`。** 不依赖 `SERIALIZABLE` 的隐式保护。
5. 死锁（`40P01`）或序列化失败（`40001`）→ **重跑完整本地事务**并保持幂等；**绝不**重复发起外部资金请求。重试上限可配置，超限转人工。

### 典型路径

```text
退款预占：    payment(20) → refund_control(30) → share_allocation(50)
              → financial_event(70) → ledger_account(80, ID 升序) → outbox(90)

争议扣款：    payment(20) → dispute(40) → share_allocation(50)
              → financial_event(70) → ledger_account(80) → outbox(90)

银行匹配：    payout(60) → bank_statement_line(65)
              → financial_event(70) → ledger_account(80) → outbox(90)

纯 BT 入账：  financial_event(70) → ledger_account(80)        ← 合法跳过业务锁
              ✗ 之后再锁 payment(20) —— 禁止，必须重开事务
```

### 多账户锁定示例

一张凭证涉及 `PSP_FUNDS`、`PSP_FEE_EXPENSE`、`SALES_REVENUE` 三个科目时：

```sql
SELECT id FROM ledger_account
 WHERE id = ANY(:accountIds)
 ORDER BY id          -- 稳定顺序，与业务语义无关
   FOR UPDATE;
```

**不能**按"借方先、贷方后"或按科目用途排序——那样两个并发事务可能得到相反顺序。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| **`SERIALIZABLE` 隔离，不显式加锁** | 高冲突下序列化失败率高，退款并发场景几乎必然反复重试；且失败时机不可预测，难以写确定性的并发屏障测试。显式锁让竞争点可见、可测。 |
| **按业务语义排序锁（先借方后贷方）** | 借贷角色随事件类型变化，同一对科目在不同事件中顺序相反 → 死锁。 |
| **每个入口自己决定顺序** | 正是死锁的来源。PR00 提示词明确要求"避免不同处理入口反向加锁"。 |
| **应用级全局锁 / Redis 分布式锁** | 单点、可能失效、不参与数据库事务。验收 §7.3 明确禁止"用一个 JVM 的 synchronized、单 Worker 配置或 Redis 锁作为通过依据"。 |
| **乐观锁（仅 version 比较）不加行锁** | 可以检测冲突但无法保证"读—判断—写"的原子性；`0<=R+H<=C` 需要在判断期间阻止其他事务改动。实际采用 `FOR UPDATE` + `version` 条件回写**双保险**。 |
| **允许账本锁之后回头加业务锁，靠重试兜底** | 重试能缓解但不能消除；且在高并发下退化为活锁，掩盖真实的设计错误。 |

## 后果

**正面**

- 死锁在设计上被排除；出现死锁即说明有代码违反 rank 规则，是可定位的缺陷而非运气问题。
- 并发屏障测试可以精确对齐关键读取/提交点（验收 §7.3）。
- 锁序表可直接作为代码评审清单。

**负面与缓解**

| 负面 | 缓解 |
|---|---|
| 某些事务锁定的行比严格必要的多 | 本项目规模下可接受；PR20 性能实验记录实际影响 |
| 开发者需记住 rank 表 | 封装 `LockOrder` 常量与获取工具；违反顺序在代码评审拦截 |
| 账本锁后不能回头，需重开事务 | 这是正确做法：重新收集全部需要的资源再按序获取 |
| `READ COMMITTED` 下需自行处理不可重复读 | 所有判断基于 `FOR UPDATE` 锁定后的读取 |
