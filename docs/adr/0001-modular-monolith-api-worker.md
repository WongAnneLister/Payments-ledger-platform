# ADR-0001：模块化单体与 API/Worker 运行角色

状态：Accepted（PR00 冻结） · 日期：2026-09-10

## 背景

系统要同时承担两类工作负载：

1. **同步请求**：创建支付、查询、申请退款、接收 Webhook——延迟敏感，必须快速返回。
2. **异步执行**：Provider 调用恢复、L1/L2 轮询、BT 导入、Outbox 发布、夜间对账——长耗时、可重试、需要租约。

同时，资金正确性要求**多行不变量在单个数据库事务内成立**（I-01～I-04、I-07）。退款预占要在一个事务里同时改 C/R/H、写退款单、写操作意图、调整分润凭证并写 Outbox。

## 决策

**采用模块化单体：同一个代码库、同一个 PostgreSQL 事务域，以不同运行角色分别启动 API 与 Worker 进程。**

```text
同一份 jar / 同一套 Flyway 迁移
   ├── 以 role=api    启动 → HTTP 入口，只做短事务
   └── 以 role=worker 启动 → 定时与租约驱动，不暴露业务写入口
```

模块包划分（PR01 建立）：
`identity` / `payment` / `provider` / `ledger` / `messaging` / `refund` / `revenue_share` / `financial_ingestion` / `dispute` / `payout` / `reconciliation` / `ops`

约束：

- 模块之间通过应用服务接口调用，**不跨模块直接操作对方的表**。
- `ledger` 模块对外只暴露 `LedgerPostingService`，是唯一过账入口（见 [ADR-0004](0004-immutable-ledger.md)）。
- Worker 角色提供受控健康检查，**不暴露业务写入口**。
- Kafka 负责传递消息，**不担任账本**；Redis 只承担可重建的缓存与限流，**不是**资金或幂等正确性的唯一依据。
- 所有外部网络调用在数据库事务之外。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| **微服务（支付/账本/对账各一个服务）** | 退款预占需要 C/R/H 与分润凭证在同一事务提交。拆服务后只能用 Saga 补偿，把一个数据库约束能解决的问题变成分布式一致性问题。本项目的核心卖点恰恰是"数据库能保证什么"，拆服务会**削弱**而不是增强论证。 |
| **单进程（API 与 Worker 同一个实例）** | 长耗时恢复任务会挤占 HTTP 线程；无法独立扩缩容；崩溃恢复实验（F-06）无法区分"API 崩溃"与"Worker 崩溃"两个不同注入点。 |
| **Serverless / 函数计算** | 租约模型需要长期持有的进程标识与可控时钟；冷启动与执行时限会干扰 F-05/F-06 的故障注入可重现性。 |
| **用 Kafka 作为事实来源** | 消息系统不提供多行事务约束。PRD §14.3 明确要求核心状态、执行义务与资金控制必须在 PostgreSQL 持久化。 |

## 后果

**正面**

- 退款、分润、争议的跨表不变量可由单事务 + 数据库约束强制，无需补偿逻辑。
- 故障实验的注入点清晰（进程崩溃、事务提交前后、消息中断）。
- 一套迁移、一套集成测试环境，PR01 的门槛可控。

**负面与缓解**

| 负面 | 缓解 |
|---|---|
| 单库成为瓶颈与单点 | 本项目目标是正确性论证，不是规模。性能实验（PR20）明确记录数据规模与配置，不宣称生产规模。 |
| 模块边界靠约定而非物理隔离 | PR03 用数据库角色权限强制"应用运行角色不能直写账本"；跨模块直接访问对方表在代码评审与测试中拦截。 |
| 单体部署耦合 | 通过运行角色分离获得独立扩缩容与独立崩溃域。 |
