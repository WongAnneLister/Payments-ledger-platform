## 1. 范围、环境与验收记录

### 1.1 实施范围

- Java 21、Spring Boot、PostgreSQL、Flyway、Kafka、Redis；模块化单体，同一 PostgreSQL 事务域，分别运行 API 与 Worker 角色。
- 一个实际组织、一个实际 Stripe 测试账户、一个结算币种。额外组织、账户和币种只用于 fixture 隔离验证。
- Stripe 托管 Checkout，一次性卡支付和自动 capture；内部合作方分润计提、争议、payout 摄入及模拟银行证据。
- 不包含 Stripe Connect、合作方实付、生产资金、银行直连、二维码、POS、完整电商目录。受控商品、价格和分润政策采用 fixture 配置。
- 客户端不提交原始卡号；金额来自可信业务订单及受控价格。Redis、Kafka 均不是资金真相源。

PR00 完成规范、契约和待验证清单，只做文档检查，构建检查不适用；PR01 开始工程实施。后续 PR 的新增行为必须包含相应基础验证，不能把所有正确性检查推迟到 PR18。PR18、PR19、PR20 分别扩展组合属性、系统故障和性能/恢复证据。

范围沿用 PRD 的明确分层：TenantScope 是组织+环境；ProviderScope 再加入 provider 账户及 livemode；MoneyScope 是组织+环境+币种；PSPControlScope 是 ProviderScope+币种+balance_type。外部对象身份及 BT 规范财务键采用 ProviderScope+对象类型/ID；币种和余额域是必须核验的事实属性，不能通过改币种或余额域绕过去重与证据冲突。

### 1.2 测试执行状态与数据完整性分开

每项检查记录两个独立字段，不能用一个绿色状态掩盖另一维度的缺失。

| 维度 | 值 | 含义 |
|---|---|---|
| `executionStatus` | `NOT RUN` | 尚未执行；本文全部条目的初始值 |
| `executionStatus` | `PASS` | 适用检查已执行，全部断言满足，所需证据齐全 |
| `executionStatus` | `FAIL` | 已观察到违反预期的行为或残差；不能因为另有缺证据而降格隐藏失败 |
| `executionStatus` | `BLOCKED` | 缺少执行前提，例如测试账户不支持能力或无法获得必要历史期末证据；必须记录阻塞原因与替代覆盖 |
| `dataCompleteness` | `COMPLETE` | 本次检查需要的范围、分页、截止点、来源证据都已固定且齐备 |
| `dataCompleteness` | `INCOMPLETE` | 任一必需证据缺失、窗口未抓完、归属不明或截止点不可比较；不代表已发现资金错误，也不代表通过 |
| `dataCompleteness` | `NOT_APPLICABLE` | 纯本地约束检查不需要外部数据完整性证据；说明适用原因 |

例子：故意缺一页 BT，系统正确输出 `INCOMPLETE`，则“能检测缺页”的测试可为 `PASS`；被测余额核对仍是 `INCOMPLETE`，不能变成“余额对账通过”。账户不支持某项真实测试时记录真实测试 `BLOCKED`，模拟用例可单独 `PASS`，不得合并声称真实能力已验证。

夜间业务报告的 `checkResult=PASS/FAIL/INCOMPLETE` 是被测产品输出，与上述测试执行状态是两套字段。夜间检查未运行时，外层仍是 `NOT RUN`，不能预填其业务结果。若完整性缺失但已发现确定违反本地约束的行为，记录明确的失败断言，同时保留数据完整性不足。

### 1.3 每次运行必须保存的证据

运行记录最少包含：`runId`、提交 SHA、规则/契约版本、依赖版本、环境、账户范围、币种、业务时区、UTC 起止边界、输入 fixture 摘要、来源模式、开始/结束时间、执行状态、数据完整性、断言结果和产物位置。

来源模式必须分别标记：

| 标记 | 可以证明什么 | 不能声称什么 |
|---|---|---|
| `LOCAL_MODEL` | 纯模型及数据库事务规则 | 真实 Stripe 行为已符合假设 |
| `PROVIDER_SIMULATOR` | 可控时钟、幂等窗口、超时、重复和外部效果计数 | Stripe 实际完成了这些压力/故障实验 |
| `STRIPE_TEST_CONTRACT` | 固定 API/SDK 与真实测试账户的少量契约记录 | 生产资金已验证，或达到负载实验吞吐 |
| `INDEPENDENT_PROVIDER_FIXTURE` | 独立模拟提供方账本/期末余额与本地账本的核对 | 真实 Stripe 期末余额验证 |
| `SIMULATED_BANK_EVIDENCE` | 银行文件解析、分配、短款和出款守恒 | 银行直连或真实银行到账 |

日志关联 businessOrderId、paymentId、refundId、operationId、provider 对象 ID、BT ID、eventId、journalId、reconciliationRunId。脱敏后保存原始证据摘要及必要字段，不在报告中记录 API key、client secret、原始卡数据或不必要的个人信息。

## 3. 七项资金不变量：提交强制与事后核对

七项 ID 和语义固定，不再额外创造“第八项”。每项可能同时具有提交约束与扫描要求，不能简单按“本地/外部”二分后遗漏其中一半。

| ID | 精确定义 | 提交时必须强制的部分 | 独立扫描/证据核对部分 | 失败处理 |
|---|---|---|---|---|
| I-01 借贷平衡 | 每张已过账凭证同币种 sum(debit)=sum(credit)，至少两条有效分录 | 受控一次性过账；提交时校验最终分录集合；拒绝空凭证、不平衡、非法金额和封存后补插 | 夜间重算每张凭证与全账试算；随机和故障序列检查 | 回滚本次入账并报警；旧账修正必须新事件、新凭证 |
| I-02 事件唯一入账 | 每个已接受规范化财务事件恰好一个 Journal；重复观察不能多记，冲正是关联的新事件 | 同范围规范事件键唯一；事件与 Journal 同事务；重复返回已有结果，冲突不能换随机键绕过 | 扫描已接受事件与 Journal 的双向覆盖；唯一键只能证明“至多一次”，必须检查无漏记与孤立凭证 | 重复保持原结果；缺失/冲突进入差错并有证据修复 |
| I-03 退款额度 | NORMAL 控制行中 0≤R+H≤C；所有本系统新发起退款先预占 | 锁支付控制行/条件更新；预占、操作意图、资格变更同事务；成功与释放幂等 | 重算 C/R/H，检查预占老化和外部退款冲突；EXTERNAL_CONFLICT 停止新退款并调查 | 拒绝本地超额；不能为维持 NORMAL 丢弃已证实外部退款 |
| I-04 分润上限 | 每合作方 0≤S_i≤floor(eligibleBase×rate_i/10000)，各比例合计≤10000 | 计提、退款预占、争议阻断及撤回按固定锁序同事务；稳定事件键和新凭证 | 读取下单快照重算累计上限、有效计提和凭证覆盖；检验碎片化退款舍入 | 撤回/拒绝超额计提，保留完整账务链，不改旧分录 |
| I-05 PSP 资金守恒 | 同账户/环境/币种/余额域/截止点：本地 PSP 余额=期初+完整 BT 净变动；并与独立 Stripe 期末证据一致 | 已接受 BT 的单次入账与 PSP 投影同事务；禁止重复更新投影 | 完整分页、独立期末证据、范围/截止一致后进行外部核对；内部模型不能替代外部证据 | 保留残差；缺证据 INCOMPLETE；不制造平账分录 |
| I-06 出款守恒 | 单 payout 已从 PSP 转出的本金=尚在途本金+已确认银行到账本金+已确认返还 PSP 本金（含经验证调整）；费用单列 | 锁定 payout/银行分配控制行，限制累计本金分配、银行行重复使用及到账/返还重叠；可立即拒绝本地超额 | PSP 与银行证据齐备后核对完整现金路线；处理净银行费用、银行退回及跨日证据 | 超额拒绝；缺证据暂挂；短款/冲突进入差错，不能双算到账和返还 |
| I-07 隔离与可重建 | 一张凭证内组织、环境、币种一致；账户余额投影=期初+对应不可变分录；同一资金来源不能跨域重复归属 | FK、账户范围和来源归属唯一约束；本地入账不能跨域；仅 LedgerPostingService 更新投影 | 独立扫描期初与分录重建，比较投影；扫描来源跨域覆盖和未分类项 | 拒绝跨域写；投影差异告警，以可审计重建纠正投影，不能改凭证迎合投影 |

银行与内部分润账户不是外部 Stripe 账户本身，不强行为每个此类账户填同一 provider_account_id；仍须明确组织、环境、币种、用途及资金来源归属。金额作用于适用的 AccountScope，不能通过账户字段可空绕过隔离。

NORMAL 控制行中的 C、R、H 各自都必须为非负整数，不能只检查 R+H 的和而允许一个负数抵消另一个超额值。

余额重建只有两种明确且互斥的计算口径：期初尚未作为 Journal 计入扫描集时，使用“经核对期初+cutoff 后分录”；期初已经用 opening Journal 入账且该凭证包含在扫描集时，从 0 累计全部分录，不能再加一次同额期初。PR00 固定默认口径，验收另外一种输入时必须显式标记，防止双计。

### 3.1 必须尝试的账本绕过路径

使用实际应用数据库角色测试，不能只调用业务方法得到“拒绝”后就认为数据库已保护：

1. 插入空 Journal、单条 Entry 和不平衡组合，分别在提交时失败。
2. 一张凭证中混用组织、环境、币种或不兼容来源，失败且不留下投影/Outbox。
3. 已封存后 UPDATE/DELETE Journal、UPDATE/DELETE Entry 均失败。
4. 已封存后插入一条 Entry，或额外插入一对借贷相等 Entry，均失败。仅保持平衡不足以保证不可变。
5. 在同事务内构造完整凭证并封存可以成功；不存在外部可修改的已提交草稿 Journal。
6. 相同规范事件重复请求返回原 Journal；改变其金额、source、fee/net 不能作为普通 duplicate 被悄悄接受。
7. 导入器、Webhook、恢复任务和对账重跑同时接受同一个 BT，PSP 投影只变化一次。Importer 不在入账服务之外另加一次余额。
8. 投影被测试管理员在隔离 fixture 中故意改错后，独立重建必须发现残差。此处是故障构造，不提供生产“改余额”路径。

## 4. 关键边界的可执行场景

### 4.1 退款与支付共用恢复流程

PR06 建立通用 provider_operation 与持久执行义务；PR07 建立唯一 recovery_task/租约重领框架；PR11 将退款接入同一机制，PR15 扩展 L3。具体 payment/refund 关联约束在 PR00 固定，退款 FK 或受约束关联表随 PR11 建立。不得各自创建不能互相观测的退款重试表和支付恢复表。

对支付与退款分别运行：

- 本地提交前崩溃：没有半个资源、没有可领取执行义务、没有孤立预占/分润凭证。
- 本地提交后、发送前崩溃：恢复器找到原操作、原请求指纹和原键，符合安全重试资格才发送。
- 提供方受理后响应丢失：保存 UNKNOWN，查询或窗口内安全重试；退款 H 保留。
- 租约到期由新 Worker 接管后旧 Worker 返回：旧 token 不更新当前控制状态，返回内容另存 provider observation；根据对象和版本规则核验后才能形成新事实。
- 提供方幂等窗口确实过期：模拟器允许原键被当成新请求；业务恢复器必须证明它没有借重发再次产生资金效果。
- 无外部 ID、持久映射或扫描不能排除远端已执行：保持 UNKNOWN/ESCALATED，告警并进入证据调查；不将“等待够久”当成安全重试证明。
- Dashboard 退款与本地预占交叠：先保存外部事实与冲突，冻结新操作；确认是否同一退款并核对资金后，用幂等调整恢复控制行。

恢复 SLA 要分“任务重新领取”和“远端业务最终完成”。本项目默认操作租约 30 秒，到期任务领取循环默认≤5秒；每 5 分钟 L2 扫描是兜底发现，不能成为唯一重领机制。在本地依赖已恢复、无账户限流、队列处于基线负载时，崩溃后 120 秒内重新领取是待验证目标；争议结果、外部 evidence 和 UNKNOWN 升级没有统一 120 秒完成承诺。

### 4.2 规范财务事件、BT 冲突与未知资金

外部观察不等于已接受财务事件。`PENDING_EVIDENCE` 或 `QUARANTINED` observation 可以没有 Journal；一旦接受为规范财务事件，就必须与完整 Journal、投影、必要 Outbox 在同一事务提交。

| 输入 | 预期处理 | 对 PSP/完整性的影响 |
|---|---|---|
| 相同 ProviderScope、相同 BT ID、相同经济事实 | 重复观察，返回原结果 | PSP 不再变化 |
| 相同 ProviderScope 和 BT ID，amount/fee/net/currency/source 等不可变事实冲突 | 保存版本与摘要，标 EVIDENCE_CONFLICT，停止自动覆盖 | 原凭证不改；改币种/余额域不能制造新键；受影响核对不能声称无冲突 |
| 相同 BT ID 字符串但不同独立 provider 账户/环境 fixture | 按 ProviderScope 独立识别，同时验证请求账户和来源归属 | 不能因 ID 字符串相同串账，也不能让同一真实来源通过另注册组织而重复归属 |
| 已核验账户/环境/币种且确定属于 payments 域，业务类型暂不识别 | 以稳定事件键把已知净变化记 PSP↔SUSPENSE，保留 UNKNOWN_SOURCE 差错 | 本域总额纳入核对；分类问题独立暴露，不把 Suspense 当已完成业务归属 |
| Treasury/其他 balance domain、FX 或归属不足 | 隔离观察，保留原始证据和未覆盖范围，不映射到 payments PSP | 不能污染本域账本；若连本域覆盖都无法确认，完整性为 INCOMPLETE |
| pending 转 available，原 amount/fee/net 不变 | 刷新可用性观察/分配 | PSP 总额不变，不生成第二次收款凭证 |
| 已暂记 Suspense 后查明业务分类 | 追加内部重分类事件及 Journal，关联原 BT/凭证 | 不重新记 PSP，不修改原 Journal |

对已知净增 700 的 payments-domain 未分类 fixture：借 PSP 700、贷 SUSPENSE 700。后续有充分销售分类证据且无需额外 PSP 变动时，以关联新凭证完成适用重分类。对净减 700 的同类 fixture：借 SUSPENSE 700、贷 PSP 700。700 只是输入，不代表 Stripe 的某个真实交易类型。

### 4.3 三层缺单与独立对账

| 检查层 | 必测输入 | 必测结论 |
|---|---|---|
| L1 延迟查询 | 已知 operation/外部 ID，丢失通知 | 按受控查询节奏找回事实；状态与财务证据分别推进 |
| L2 本地扫描 | UNKNOWN、租约过期、缺 BT、长时间处理中 | 重领持久义务，老化告警，不依赖内存队列 |
| L3 外部枚举 | 外部成功且缺本地 payment；另一个案例连业务订单也缺 | 前者需可信订单等全部资格满足才恢复；后者仅未分配财务观察，不虚构订单/履约 |
| 交易级核对 | source/金额/状态不一致 | 定位业务映射冲突，保留证据，不只比较总余额 |
| 余额级核对 | 少一 BT、漏费用、重复投影、错期初、错截止点 | 各自被检出；完整数据下报告残差，缺必需数据时报告 INCOMPLETE |
| payout/银行核对 | 缺银行行、短款、重复行、到账后返还 | 区分待证据、短款和冲突，不将 paid 当银行确认 |

I-05 至少有三份可比输入：期初及 BT 明细、本地不可变账本/重建余额、独立期末证据。由同一份导入 BT 生成两次汇总不算第三份证据。内部独立 oracle 可以检出本地算法错误，但只有独立外部期末证据能检查导入覆盖是否遗漏。

真实环境优先使用对应期间、范围和截止点的报告；当前 Balance API 快照不能冒充昨日历史期末。若仅能在可控静止区间获得快照，要保存“无其他资金变动”的窗口证据，并按该 cutoff 比较；无法做到则运行保持 INCOMPLETE。独立模拟提供方账本与独立模拟银行文件可用于 fixture 验证，必须如此标注。

## 5. 可以手算的两条演示路线

共同约定：USD 最小单位整数，期初全零，收款 10000、实际 charge fee 300、20% 分润。所有数字均为 fixture；费用不是 Stripe 实际报价。每行代表一张平衡 Journal 或一次不涉及 PSP 的控制状态变化。支付成功、BT 入账、余额 available 与银行到账分开演示。

路线 A 与路线 B 是不同测试实例；争议、退款失败和 payout 失败均有分支，不能把每个表格事件串成一笔现金路线。

### 5.1 路线 A：收款 → 部分退款成功 → payout → 模拟银行到账

| 步骤 | 事实与借方 | 贷方 | 步骤后关键结果 |
|---|---|---|---|
| A1 | Charge BT：借 PSP_FUNDS 9700；借 PSP_FEE_EXPENSE 300 | SALES_REVENUE 10000 | C=10000；PSP=9700；R=H=0 |
| A2 | 收款证据齐备，借 PARTNER_SHARE_EXPENSE 2000 | PARTNER_PAYABLE 2000 | cap=S=2000 |
| A3 | 预占退款 4000，借 PARTNER_PAYABLE 800 | PARTNER_SHARE_EXPENSE 800 | H=4000；R=0；eligibleBase=6000；cap=S=1200；PSP 仍为 9700 |
| A4 | Refund BT：借 SALES_RETURNS 4000 | PSP_FUNDS 4000 | 退款确认成功后 H=0、R=4000；PSP=5700；H→R 不重复撤回分润 |
| A5 | payout 本金 5700 的扣减 BT：借 BANK_PAYOUT_IN_TRANSIT 5700 | PSP_FUNDS 5700 | PSP=0；在途=5700；银行=0 |
| A6 | 模拟银行证据确认 5700：借 BANK_CASH 5700 | BANK_PAYOUT_IN_TRANSIT 5700 | 在途=0；银行=5700；payout 本金全额匹配 |

可用性前置：A5 只有在 fixture 表明对应金额可出款且有实际扣减 BT 时发生。pending→available 不改变 A1～A4 的 PSP 总额。payout.paid 可以先到或后到；它本身不产生 A6。

最终手算：

- 退款：`R+H=4000+0≤10000`。
- 分润：`eligibleBase=10000-4000-0=6000`，`cap=floor(6000×2000/10000)=1200`。
- PSP：`0+9700-4000-5700=0`，还需与同截止点独立提供方期末证据 0 比较。
- payout：`5700=在途0+确认银行本金5700+返还0`。
- 期末借方余额：银行 5700 + 收入抵减 4000 + PSP 费用 300 + 分润费用 1200 = **11200**。
- 期末贷方余额：销售收入 10000 + 合作方应付 1200 = **11200**。
- 本路线各 Journal 借方发生额合计与贷方发生额合计均为 **28200**。它与期末净余额试算的 11200 是不同统计，不能混用。
- 演示净收益：`10000-4000-300-1200=4500`；银行 5700 中仍含未实付的合作方应付 1200。Stripe payout 没有结清分润。

单独的 payout 失败分支从 A5 开始，**不执行 A6**：失败返还 BT 借 PSP_FUNDS 5700、贷 BANK_PAYOUT_IN_TRANSIT 5700，最终 PSP=5700、在途=0、银行=0，守恒为 `5700=0+0+5700`。不得再套用路线 A 的“银行=5700”。

### 5.2 路线 B：退款失败恢复，随后另选争议分支

新建独立 fixture，重复 A1/A2 的收款与首次计提，不创建路线 A 的 payout。初始 PSP=9700、S=2000。

| 步骤 | 控制状态与账务 | 结果 |
|---|---|---|
| B1 | 预占 4000，同事务借 PARTNER_PAYABLE 800、贷 PARTNER_SHARE_EXPENSE 800 | C=10000、R=0、H=4000；S=1200；PSP=9700 |
| B2 | 远端已受理但超时，退款 UNKNOWN | H 保持 4000；不补造退款 BT；不恢复分润、不新建退款 |
| B3 | 本分支收到扣减 BT：借 SALES_RETURNS 4000、贷 PSP_FUNDS 4000；退款尚未最终成功 | PSP=5700；R/H 仍按经核验状态更新，不能用 BT 直接假装业务成功 |
| B4 | 明确 FAILED：幂等释放 H；无其他阻断时借 PARTNER_SHARE_EXPENSE 800、贷 PARTNER_PAYABLE 800 | R=0、H=0、eligibleBase=10000、S=2000；失败状态本身不把 PSP 加回 |
| B5 | 新的失败返还 BT：借 PSP_FUNDS 4000、贷 SALES_RETURNS 4000 | PSP=9700；SALES_RETURNS 净额=0；原 charge fee 300 仍存在 |

B4 与 B5 可以乱序到达，缺依赖或矛盾进入待证据/调查；恢复分润还必须满足无阻断争议、无未解决资金矛盾和已具备收款记账证据。重复 B4/B5 不再释放额度、计提或增加 PSP。

另一种“退款在产生扣减 BT 前就明确失败”的子用例只做 B1、B2、B4，没有 B3/B5，不制造一减一加的假资金变动。两种失败用例的最终 PSP 都是 9700、分润 2000，但账务历史不同。

B5 完成后的期末借方余额：PSP 9700 + PSP 费 300 + 分润费 2000 = **12000**；贷方：销售收入 10000 + 合作方应付 2000 = **12000**。银行和出款在途均为 0。

从该恢复节点再复制三个独立争议 fixture：

| 分支 | 分录与控制行为 | 最终可核验余额 |
|---|---|---|
| 开案但无扣款 BT | 撤回全部 2000 分润：借 PARTNER_PAYABLE、贷 PARTNER_SHARE_EXPENSE；存在阻断时 eligibleBase=0；inquiry/warning 无扣款证据不减少 PSP | PSP=9700；S=0；普通退款被阻止；不能凭状态构造争议应收 |
| 正式扣款后胜诉 | 实际 BT 借 DISPUTE_RECEIVABLE 3000、借 DISPUTE_FEE_EXPENSE 1500、贷 PSP_FUNDS 4500；返还本金 BT 借 PSP_FUNDS 3000、贷 DISPUTE_RECEIVABLE 3000；状态及资金证据齐备且无其他阻断后重新计提 2000 | 扣款后 PSP=5200；胜诉后 PSP=8200、应收=0、S=2000；争议费 1500 无返还证据则保留 |
| 正式扣款后败诉 | 同样先发生扣款与分润撤回；lost 时借 DISPUTE_LOSS 3000、贷 DISPUTE_RECEIVABLE 3000，PSP 不再扣款 | PSP=5200；应收=0；争议损失=3000；争议费=1500；S=0 |
| 上一败诉分支发生 late win | 新返还 BT 借 PSP_FUNDS 3000、贷 DISPUTE_LOSS 3000，并关联原损失；won 与相关资金证据齐备且无其他阻断后可重新计提 | PSP=8200；损失净额=0；应收=0；S=2000；争议费仍=1500 |

上表“开案但无扣款”可作为各争议生命周期的前置节点；胜诉和败诉互斥，late win 只能接在对应败诉分支后。不能把正常胜诉返还与 late win 返还各加一次。

额外分配 microfixture：同一关联争议尚存应收 1000、已确认损失 2000，收到本金返还 3500，则借 PSP 3500；贷争议应收 1000、贷原争议损失 2000、贷 Suspense 500。优先级是**尚存应收 → 已确认损失 → 超额待解释**；不得直接贷损失 3500。超额差错未解决时不据此自动恢复分润。

### 5.3 已银行匹配又收到 payout 返还

这是单独冲突 fixture：原本金 5700 已匹配银行，然后发现真实返还 BT 5700。两份事实都保留，但不能直接把“确认到账5700+确认返还5700”当成该 payout 的本金分配。

- 锁定 payout 控制行，阻止超额分配和新自动出款；保存 CONFLICT。
- 真实、已核验本域的 PSP 返还必须保留资金影响；在途已为零时，未解决对应关系可先以明确暂记规则入 Suspense，不能把在途减成负数来假装匹配成功。
- 取得银行退回等证据后，追加调整并修正净分配关系；原银行入账与原 payout Journal 均不删除。
- 若银行确实退回 5700，可按已冻结政策追加银行减少与暂记解除，并得到银行净到账 0、PSP 返还 5700。没有银行证据时继续等待/冲突，不能先假定银行现金已经减少。

具体暂记与调整事件键在 PR00 会计规则表冻结，PR14 实施；测试必须同时检查原始事实、净分配和审计链。

## 7. 属性测试与真实数据库并发

### 7.1 独立 oracle

候选工具为 Java 属性测试库，具体依赖版本在 PR00/PR01 固定。生产服务与 oracle 只能共享基础数据类型或不可变输入 schema，不共享金额公式、分润计算器、状态迁移函数、事件归一化函数及投影实现来计算预期结果。

独立纯模型至少维护：业务订单与 capture、C/R/H、争议阻断与应收/损失、合作方比例快照与净计提、独立提供方资金效果、PSP 净变动、payout 本金分配和银行净证据。纯模型不能读取生产 projection 作为真相，也不能从生产 Journal 抄出预期值。

三种“独立”要分别证明：

1. **算法 oracle**：通过另一份简洁数学模型计算预期业务结果，用于发现实现错误。
2. **账本重建器**：直接扫描不可变分录与期初，绕开生产 projection 更新路径，用于发现投影漂移。
3. **外部期末证据**：独立提供方账本/报告/快照和银行证据，用于发现 BT 获取遗漏或外部余额不一致。

前两种不能代替第三种。fixture 外部账本应在测试开始由独立交易序列产生并固定摘要，再由适配器暴露分页视图；故意漏掉一页时，外部期末证据仍保留完整余额，才能检出导入丢失。

### 7.2 操作生成与断言时点

生成合法及应拒绝命令：支付成功/拒绝/未知，客户认证，多 attempt，取消竞争，退款预占/成功/失败/超时，外部退款，分润计提/撤回/恢复，争议扣款/won/lost/late win，多争议与退款重叠，payout/失败返还/银行部分匹配，未知 BT，重复乱序、崩溃及幂等窗口过期。

| 时点 | 断言 |
|---|---|
| 每次已提交本地事务后 | I-01 平衡；I-02 唯一及本次原子关联；I-03 NORMAL 额度；I-04 上限；I-07 隔离；I-06 本地分配不超额 |
| 非法命令被拒绝后 | 没有新增资金操作、预占、分润凭证、Outbox、银行匹配或余额变化；已有合法事务效果不被撤销 |
| 外部事实暂未完整时 | UNKNOWN/WAITING_EVIDENCE/CONFLICT 可解释；不以“尚未收敛”断言外部余额必须相等，也不能虚假 PASS |
| 完成有限输入并排空可执行任务后 | 已接受事件覆盖完整；模型、重建与投影一致；证据齐备时 I-05/I-06 成立；未解决例外明确报告 |
| 无法安全自动恢复时 | 没有无依据资金写入，存在持久升级任务和报警；不能用无限重试假装收敛 |

PR 套件目标：100 个 seeds、每序列最多 100 步。夜间目标：1000 个 seeds、每序列最多 300 步。实际数量按 CI 预算记录，可调整但不能将目标数字直接填入结果；还须报告生成分布，避免数量足够但始终未生成争议/过期键等关键分支。

### 7.3 并发屏障测试

串行随机序列不能证明数据库并发安全。至少两个实际连接、两个 API/Worker 进程，在实际 PostgreSQL 上使用同步屏障对齐关键读取/提交点，并保存调度和事务结果：

| 并发输入 fixture | 可接受结果 | 禁止结果 |
|---|---|---|
| C=10000、R=H=0，同时申请 7000 与 5000 退款 | 按锁序最多一个请求成功，另一明确额度不足；若重试必须保留幂等语义 | 两者都预占成功，或先远端发送再发现超额 |
| C=10000、S=2000，同时预占退款 4000 与重新计提 | 无论先后，最终 cap=S≤1200；追加凭证与 H 原子一致 | H=4000 但 S=2000；凭证已提交而 allocation 未改 |
| 未决争议到达与新普通退款 | 按固定锁序确定提交顺序；争议已生效后禁止新退款；已提交义务与外部事实如有交叠进入调查 | 靠内存标记忽略已提交退款或丢弃真实争议 |
| 两 Worker 同时恢复同一 operation；第三个旧 Worker 回写 | 只有有效租约更新控制状态，外部操作符合安全重试资格，所有观察可追踪 | 旧结果覆盖新状态、换键制造另一笔操作 |
| Webhook、BT 导入器、恢复器同时接受同一事实 | 单规范事件、单 Journal、单投影变化 | 唯一 Journal 但余额被三个入口各加一次 |
| 银行一行 5700 被同时匹配到两个 payout | 同一行来源约束及累计分配允许的总额≤5700 | 每个 payout 各获 5700，重复确认现金 |

隔离级别、锁顺序、重试上限和幂等语义在 PR00 冻结。不能用一个 JVM 的 synchronized、单 Worker 配置或 Redis 锁作为通过依据。

### 7.4 失败反例与 mutation

真实失败保存 seed、完整序列、调度、shrink 最小反例、期望/实际结果、修复提交及回归用例。若未发现真实缺陷，就报告“本次实际 N 个 seeds/M 步未发现失败”，不填“发现 3 个缺陷”。

测试敏感性可以故意注入“退款预占未撤回分润”“重复更新投影”“lost 再扣 PSP”“封存后允许追加平衡 Entry”等错误实现；记录为 mutation 及检出结果，不能计为真实发现的产品缺陷。发现真实问题允许最小修复或独立修复 PR，不得改变业务规则迎合测试。

## 8. 夜间七项检查

每个启用账户按配置业务时区运行，固定 `runId`、输入高水位、账本 cutoff、外部证据 cutoff、规则版本、数据完整性和残差。重跑使用可复算输入版本，晚到证据使受影响日期重新核对。

| 检查 | 主要输入与计算 | 正常输出 | 不完整/失败示例 |
|---|---|---|---|
| 试算平衡 | 独立扫描已封存 Journal/Entry，逐凭证与总账重算，并扫描事件覆盖 | 凭证平衡、无孤立已接受事件/凭证 | 不平衡或已接受事件缺 Journal 为 FAIL |
| 账户余额重建 | 从期初与分录重建每范围账户余额，与 projection 比较，并检查跨域来源 | 每范围残差 0 | 投影多加一次、来源跨域重复为 FAIL |
| 退款预占老化 | 重算 C/R/H、NORMAL 约束、未决操作和租约年龄 | 额度成立且超龄均有明确处理/告警 | 超额为 FAIL；无告警的失联预占为 FAIL；外部未知保留状态 |
| 分润上限 | 读取订单政策快照与退款/争议事实，重算 cap 与有效计提及凭证覆盖 | 所有 S 在合法范围，调整凭证齐全 | 预占后超计提、乱序重复恢复为 FAIL |
| BT 覆盖 | 固定范围/窗口全部页面、游标、外部事实集合与本地规范事件覆盖 | 全分页完成，已接受事件无漏账，未分类项显式列出 | 缺页/范围不明为 INCOMPLETE；确定漏记/重复为 FAIL；Suspense 分类差错不得隐藏 |
| PSP 余额核对 | 期初+完整 BT、账本重建、独立期末证据在同 cutoff 比较 | 余额一致且完整性满足 | 缺独立期末为 INCOMPLETE；完整证据下残差非零为 FAIL |
| payout 在途核对 | 本金、返还、净银行确认、银行费、在途与逾期 | 本地分配合法；完整证据下守恒；逾期有工单 | 银行缺证据为 INCOMPLETE；重复分配/已知短款未处理为 FAIL |

报告同时呈现未分类数、待证据数、失败数与完整性，不能把“程序跑完了”当作全部通过。总体完成条件要求所有适用断言有可追溯结论；非零残差必须保留原因和处理路径，禁止自动加 OPENING_EQUITY 或随机 adjustment 清零。

### 9.1 性能实验目标

使用本地提供方模拟器：两个 API 与两个 Worker 实例、100 万历史支付、写受理 100 RPS + 查询 200 RPS、预热 5 分钟、运行 30 分钟。目标本地受理 P95≤300ms、P99≤1s，非注入错误率<0.1%。以上全部是待验证目标；硬件不足或目标未达时如实记录实际配置和结果。

同时检查零重复模拟 capture 效果、零本地新发起超额退款、零重复规范财务 Journal、零不平衡凭证。记录 UNKNOWN 老化、Outbox 队龄、Worker 租约和对账残差；不能用平均吞吐掩盖重复资金效果，也不能把 HTTP 受理吞吐写成已完成支付吞吐。不得向 Stripe 测试环境发送该负载。

### 9.2 备份恢复演练

仅在新项目的显式隔离测试库操作，不能删除、迁移或覆盖其他项目数据库。演练前记录目标库名与隔离依据、备份时刻及外部模拟器独立持久状态。

1. 获取一致备份，保存其摘要、版本与 cutoff。
2. 备份后继续产生支付/退款/外部资金效果，再模拟本地数据丢失；外部状态不回滚。
3. 恢复到新的隔离目标库，保持资金写操作受限。
4. 独立重建账本，检查事件覆盖与投影，重扫外部范围并检测备份后事实。
5. 仅按可信订单、安全操作键资格和证据恢复；过期未知操作升级调查。
6. 验证恢复后外部效果未重复、资金残差有解释，再恢复符合资格的写流程。

记录实际 RPO、RTO、重扫范围、无法自动恢复记录和人工步骤。不能只展示数据库可启动，或通过重置模拟器外部状态消除本地/外部差异。

### 9.3 英文演示与完成门槛

演示必须能从隔离空环境重放路线 A、路线 B 的选定分支、UNKNOWN 恢复、一次丢单 L3 回补以及一次独立余额差异检测。英文页面、README 和口述均标明测试资金与模拟银行证据。

项目完成前核对：

- 38 项矩阵逐项有实际状态与产物；BLOCKED 能力单列，不能因模拟通过而自动改 PASS。
- 七项不变量的提交强制与证据核对各有对应实现及验证，不声称分布式系统端到端 exactly-once。
- 八类故障分别可复现，属性/并发结果保存真实运行数据。
- 真实 Stripe 契约与模拟故障、独立期末 fixture、模拟银行证据清楚区分。
- 性能与备份恢复报告保存实际结果，未达到目标照实说明。
- 简历主张能追到 runId/代码版本/报告；第一人称完成时和数字只在证据存在后填写。
