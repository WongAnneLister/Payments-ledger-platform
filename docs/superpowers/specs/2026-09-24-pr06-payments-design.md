# PR06 business payment design

Execute the accepted PR06 prompt and frozen OpenAPI/state machines after PR05. The user's continuation authorizes this next bounded implementation; no change to product scope or previously frozen decisions.

A payment starts with a trusted TenantContext, server-controlled product price, validated quantity and immutable full policy snapshot. Canonical request fingerprints include all semantic fields (normalized quantity/defaults, sorted metadata, URLs and customer reference). PostgreSQL independently enforces API-key uniqueness and application order-key uniqueness. Identical API replay returns the same current resource; a new API key for an existing order returns ORDER_INTENT_CONFLICT. A stale policy/price must not invalidate replay of the original accepted request.

Use business_order, payment, api_idempotency_record, provider_operation, payment_attempt, recovery_task, and append-only provider_observation. Composite FKs preserve org/environment/application/provider/currency association. Provider operation uses payment_id/refund_id XOR; REFUND remains forbidden until PR11 installs its FK. Persist immutable provider command parameters including the absolute Checkout expiry and distinct stable create/expire keys. Order policy snapshot cannot be edited after creation.

PaymentService commits intent, operation and execution task together, then invokes a small executor outside the transaction. A worker can claim PREPARED tasks after a crash. Claim is a short database transaction, with a persisted token/version; only its current operation/version may write control state. Unknown/SENDING operations are retained, never automatically resent; PR07 owns lease recovery and L1/L2. Every provider response, including stale results, retains redacted evidence in provider_observation. No JVM/global Redis lock substitutes for database uniqueness.

GET performs a scoped database query and, when a Session reference exists, an authoritative provider refresh outside the transaction. Session, PI and complete Charge attempt history are checked for association/currency/amount. Capture is sticky; failed attempts never erase it. A successful payment remains PENDING_EVIDENCE (no journal posting in PR06). Unknown responses preserve last known provider status and suppress a payment redirect that could prompt duplicate action.

Cancel persists a distinct idempotent intent before any query/expire call. Expire is called only for a verified open session. Any PI or accepted-funds ambiguity requires complete query evidence or UNKNOWN/CONFLICT. Successful capture cannot be canceled. No direct PI cancel and no refund. A response saying expired without sufficient no-funds evidence never erases success.

Expose authenticated POST /v1/payments, GET /v1/payments/{id}, POST /v1/payments/{id}/cancel. Return the frozen PaymentResource and NextAction; 201 only for a known hosted session, 200 for replay, controlled provider/persistence errors otherwise. Keep a durable resource reference on uncertain outcomes. A minimal static same-origin test client accepts the application credential in page memory, creates an order, links to hosted Checkout, and queries after return. No anonymous payment resource endpoint or secret in redirect URLs.

Validation is strict: reject unknown fields and floats-as-integers, positive bounded quantity, checked multiplication, uppercase configured currency, valid HTTPS return URLs without userinfo, bounded keys/text/metadata and reserved internal metadata protection. Provider credentials/account come only from trusted configuration. No new provider SDK use outside adapter.

Verification uses real isolated PostgreSQL, test runtime role, 100 concurrent requests, independent order/API uniqueness, changed payload conflict, snapshot immutability, forged scope/amount, overflow/JPY, multiple attempts, sticky capture and cancel races, persisted tasks across executor restart, stale results and provider-outside-transaction assertions. Test-only Fake and real Stripe results stay separate. A small opt-in real API create/query/expire check verifies the new application path; it does not repeat a card charge. R0 gaps stay BLOCKED and PR07/08/10 responsibilities remain explicit.
