## 1. 开工方式

新建独立 Java 工程，从业务规则、API 契约、数据库迁移到测试全部自行实现。不使用、复制、扩展或研究 Jeepay 代码，不迁移旧系统的数据、状态常量或数据库。本文只定义工作顺序，没有创建仓库、执行迁移或完成任何代码。

采用 Java 21、Spring Boot、PostgreSQL、Flyway、Kafka、Redis。具体框架、驱动、SDK 和基础设施版本由 PR00 记录候选与依据，PR01 和 PR05 验证后锁定；不以“最新版本”代替版本号。采用模块化单体，同一代码库分别启动 API 和 Worker 运行角色，共享同一 PostgreSQL 事务域。外部网络请求放在数据库事务外；Kafka 负责传递消息，Redis 不作为资金或幂等正确性的唯一依据。

实际联调仅使用一个 Stripe 测试账户、一个组织、一个运行币种；额外组织、账户和 JPY 场景通过隔离 fixture 验证。使用托管 Checkout，不收集卡号。商品、价格及分润政策使用受控配置/fixture；不建设完整电商目录、门店、二维码、POS、Connect、合作方实付或真实银行直连。

这组六个文件未来放入独立仓库的 `docs/product/`；OpenAPI 放入 `docs/contracts/`，状态机放入 `docs/state-machines/`，架构决策放入 `docs/adr/`。文档所在目录不会被自动当成新工程根目录。

## 4. 容易遗漏的集成边界

### 4.1 真实 Stripe 不留到最后

PR04 是故障模拟器，PR05 才是实际适配器。PR05 要验证冻结版本中的 Checkout 创建/过期、对象映射、metadata、退款接口、BT/争议/payout/余额读取和签名原始 fixture。账户没有相应能力时，标注 BLOCKED 或 fixture-only，保存原因与替代实验，不使用模拟成功代替真实成功。

PR06 使用 PR05 的真实适配器提供最小托管跳转与结果查询。创建 Checkout 会话只表示客户可以继续支付，不表示已经扣款。完整运营页面在 PR17，首个客户支付入口不等到 PR17。

### 4.2 只有一套操作恢复框架

PR06 先把业务订单、payment、provider_operation 和持久执行义务放在同一事务。PR00 决定操作关联模型：payment/refund 互斥外键关联，或有数据库约束的关联表。PR07 唯一创建 `recovery_task` 并支持租约、重领、查询与升级；PR11 接入退款；PR15 扩展 L3。不得为退款再建一套无法被通用 Worker 恢复的操作体系。

默认 L1 使用 5/15/30/60/120 秒退避并加抖动、账户限流；L2 每 5 分钟扫描已知本地异常；L3 次业务日处理前日窗口并重叠回看。它们是项目策略，不能表述为 Stripe 结算承诺或所有异常的恢复时限。

### 4.3 BT 记账与分润分阶段闭合

PR03 是唯一修改余额投影的过账入口。PR10 BT Importer 调用该入口，不再额外累加 PSP 投影。Charge BT 先接收款；Refund BT 的基础会计映射同时落地，但没有退款业务关联时保留观察与依赖等待。PR11 补齐退款创建、外部退款观察、成功/失败返还和通知接线；状态事件本身不能虚构 PSP 分录。

PR11 期间不启用分润。PR12 使用 PR06 下单快照，在收款 BT 已正式入账后初次计提，并在退款预占、成功、明确失败/取消、UNKNOWN 恢复和外部冲突路径里，原子提交 allocation、新财务事件及追加 Journal。已有收款 BT 的订单通过稳定键 catch-up，不能因上线次序漏计提。完成上述接线和测试才允许启用分润。

PR12 预留争议阻断能力；PR13 把争议观察、扣款、退款禁止、分润撤回、胜诉且证据齐备后的恢复接入同一业务控制锁序。争议的状态和扣款不是两个可重复减少 PSP 的来源。

### 4.4 资金可解释需要独立证据

PR14 先实现银行 fixture 导入核心和匹配，再由 PR16 暴露受权限控制的运营 API。`payout.paid` 不直接确认银行现金；银行到账和返还 PSP 的本金分配总额不能超过已转出本金，重叠事实进入冲突处理。

PR15 对账固定 AccountScope、UTC 窗口、业务时区、输入高水位、规则和证据版本。BT 构建的账本与同一 BT 求和只能检查内部一致性；余额核对还需要独立、同截止点的外部期末报告或受控静止区间快照。测试 oracle 与外部期末证据也分别说明来源。没有完整分页或可比证据时为 INCOMPLETE，不制造“平账分录”。

## 5. 每个 PR 的工作纪律

1. 先读取 PRD、当前验收和依赖实现，检查工作区既有改动；没有 Git 仓库时如实记录，不凭空报告状态。
2. 列明当前修改点、迁移与约束、事务与锁顺序、接口与错误、测试计划，然后直接实施当前已授权范围；只有真正缺失且会影响核心语义的信息才升级。
3. 表字段清单是设计重点，实施可以补齐外键、scope、审计、版本、时间戳和索引。允许修改已有 Controller、Handler、Service、迁移后的新迁移和测试来完成当前接线，不使用“只能新建这些文件”限制。
4. 基础正确性测试随模块交付：账本在 PR03，租约在 PR07，退款在 PR11，分润在 PR12。PR18 扩展跨域模型，PR19 汇总故障实验，不把关键保护拖到最后。
5. 已发布迁移不原地重写；需要修改约束时追加迁移。只对明确新建的隔离测试库执行重建或恢复，验证完整目标连接和库名，禁止宽泛删库。
6. 测试结论用 PASS/FAIL/NOT RUN；适用但未运行的测试是 NOT RUN，不能算完成。确实不适用于当前 PR 的检查用 N/A 并说明。BLOCKED 用于能力/环境受阻的状态，不能冒充通过。
7. PR00 只验证文档、链接、契约与手算例；构建和数据库重建为 N/A。代码 PR 运行相关测试、构建、适用的隔离迁移检查和差异检查，记录实际结果。
8. 最终报告列已完成内容、未通过或未运行项目、AC-V1 证据路径与后续接线。发现真实缺陷允许最小范围修复并补回归，不能更改业务不变量使测试通过。
