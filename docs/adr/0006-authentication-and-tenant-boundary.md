# ADR-0006：认证与租户边界

状态：Accepted（PR00 冻结） · 日期：2026-09-10

## 背景

系统有三类完全不同的调用方：业务应用、运营人员、Stripe 回调。它们的身份来源、权限模型与失败语义都不同。

最常见的错误是**把请求内容当作授权依据**：从请求体里读 `organization_id` 然后据此查询。这等于让调用方自己声明自己是谁。

## 决策

**身份一律由凭据解析，请求内容永不作为授权依据。**

### 三类入口

| 入口 | 认证方式 | 身份来源 | 失败语义 |
|---|---|---|---|
| `/v1/**` | `Authorization: Bearer <application_secret>` | `application_credential` → TenantContext | 401 / 403 / 404 |
| `/ops/**` | `OpsBearer`（独立凭据表 / OIDC） | `ops_identity` + 角色 | 401 / 403 |
| `/webhooks/stripe` | **无 Bearer**；`Stripe-Signature` 对原始字节验签 | endpoint 绑定的 ProviderScope | 400（无副作用）/ 503（可重试） |

### TenantContext

凭据解析出**不可覆盖**的上下文：

```text
organization_id / environment_id / application_id
allowed_provider_account_id / allowed_currencies[] / livemode / granted_scopes[]
```

强制规则：

| # | 规则 |
|---|---|
| A1 | 请求体/参数/Header 中的归属字段：与 TenantContext 不一致 → `403`；一致 → **忽略**（不作为授权依据） |
| A2 | 缺失/过期/吊销凭据 → `401`，且**不泄露**资源是否存在 |
| A3 | 跨组织读取 → **`404`**（非 403），避免通过状态码差异枚举他人资源 ID |
| A4 | 跨组织写入在数据库层还有复合 FK / CHECK 兜底 |
| A5 | `livemode=true` 的配置在**进程启动时**即拒绝，不是请求级检查 |
| A6 | 应用凭据只存 Argon2id/bcrypt 摘要，不存明文 |
| A7 | API key、client secret、完整 token、卡号、银行敏感字段**不进日志** |

### 运营权限与审批分离

| 角色 | 只读 | 回补/导入 | 异常/重试 | 调整申请 | 调整审批 |
|---|---|---|---|---|---|
| `OPS_VIEWER` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `OPS_OPERATOR` | ✅ | ✅ | ✅ | ✅ | ❌ |
| `OPS_REVIEWER` | ✅ | ❌ | ❌ | ❌ | ✅ |
| `OPS_ADMIN` | ✅ | ✅ | ✅ | ✅ | ❌ |
| `PARTNER_VIEWER` | 仅自身 `partner_id` | ❌ | ❌ | ❌ | ❌ |

**审批分离是硬约束**：`created_by <> approved_by`，由数据库 CHECK **与**应用双重强制。`OPS_ADMIN` 拥有其他全部写权限，**仍然不能**审批自己的申请。

**不存在**直接修改已过账凭证或直接改余额的接口——这不是权限问题，是接口根本不提供。

### Webhook 顺序

```text
1. 用原始字节 + Stripe-Signature 验签      ← 禁止先反序列化再重新序列化
2. 校验事件 account/livemode 与 endpoint 绑定的 ProviderScope 一致
3. 短事务唯一写入 webhook_inbox
4. 持久化成功后才返回 2xx
```

持久化失败**必须**返回 5xx，**不得**返回 200 假装已接收。

## 被否方案

| 方案 | 为什么否 |
|---|---|
| **从请求体读 `organization_id`** | 调用方自称身份，跨租户越权门户大开。PRD §14.1 明确禁止。 |
| **业务凭据与运营凭据共用一张表/一套 scope** | 业务应用可能通过 scope 提升触达运营写接口；两者的生命周期、轮换策略、审计要求也不同。 |
| **跨组织访问返回 403** | 403 与 404 的差异可用于枚举他人资源 ID 是否存在。统一 404。 |
| **Webhook 也要求 Bearer** | Stripe 不发送自定义 Bearer；签名验证才是其真实身份机制。加 Bearer 只是伪安全。 |
| **先 JSON.parse 再验签** | 序列化往返会改变字节（键顺序、空白、数字格式），签名必然失效或被绕过。 |
| **Webhook 同步完成账务后再返回 200** | HTTP 超时会导致 Stripe 重投，而本地可能已部分入账；且长事务持锁。应当只持久化后立即 2xx，异步处理。 |
| **`OPS_ADMIN` 可以审批自己的申请** | 双人复核失去意义。PRD §3.2 明确"复核员不能审批自己创建的调整"。 |
| **在请求级检查 live 凭据** | 配置错误应当在启动时暴露，而不是等到第一笔真实资金请求。 |

## 后果

**正面**

- 跨租户越权在应用层与数据库层双重拦截。
- 权限矩阵可直接转成正反用例测试表。
- Webhook 的"验签→持久化→应答"顺序使 F-04（篡改）与 F-01（丢失）的断言清晰。

**负面与缓解**

| 负面 | 缓解 |
|---|---|
| 调用方无法自选组织（多组织场景不便） | 本期单组织；多组织用 fixture 隔离验证 |
| 404 掩盖真实原因，增加调试难度 | `requestId` 关联服务端日志，日志中记录真实原因 |
| 启动时拒绝 live 导致部署失败 | 这是期望行为；错误信息明确指出是本期范围限制 |
| 审批分离在单人开发时不便 | 测试用两个 ops 身份 fixture |
