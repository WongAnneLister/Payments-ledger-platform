# Stripe 支付与复式账本：从零实施文档包

版本：1.1 · 日期：2026-09-10 · 状态：规划已修订，业务代码和实验尚未实施。

这套文档按“独立新项目”编写：新仓库、新代码、新数据模型、新迁移和新测试，不使用或参考 Jeepay。当前交付的是可用于开工的文档，没有创建应用工程，也没有宣称 Stripe 账户、构建或资金测试已经通过。

## 1. 文档怎么改了

| 原规划的缺口 | 本版修改 | 开发时的直接作用 |
|---|---|---|
| PRD、路线图、验收表分别描述不同代方案 | 统一到 Java 21、Spring Boot、PostgreSQL、Flyway、Stripe；从零模块化单体，API/Worker独立运行 | 不再研究旧订单状态、迁移旧表或兼容已有代码 |
| 验收编号指向旧场景 | 重建 AC-V1-01～AC-V1-38，保留七个 I 和八个 F 的含义 | 每个新版PR都有可验证的验收归属 |
| 只有 Fake Stripe 的明确任务 | PR05 单独实现真实 StripeAdapter 和小规模测试环境契约验证 | Checkout入口、对象关联、metadata、取消、退款和财务读取不再无任务负责 |
| 创建支付与客户完成付款混在一起 | PR06区分业务订单、托管Session、支付尝试及最终capture事实 | 创建会话不会被记成一次扣款成功 |
| 业务订单的权威金额和政策来源模糊 | PR02配置受控价格/政策fixture，PR06验证并保存订单与政策快照 | 测试“客户端不能改价”有真实规则可测，不扩张为电商商品系统 |
| 退款UNKNOWN没有完整恢复归属 | PR07建立通用操作恢复；PR11把退款查单、租约、未知保留和通知接入 | 不会出现支付能恢复、退款永久占额的两套实现 |
| “一直重用原key”掩盖远端key过期 | Fake模拟保留窗口；真实适配记录版本契约；未知且可能过期时调查/升级 | 能证明安全边界，而不是依赖模拟器永久去重 |
| 分润仅列计算函数，缺记账动作 | PR12完整实现首次计提、撤回、恢复的稳定财务事件和新凭证 | 分润额度、合作方应付与账本能复算；不涉及合作方实付 |
| BT导入可能漏未分类金额或重复更新余额 | PR10区分可验证payments域暂记与其他域隔离；投影仅由过账服务更新 | 不用未知类型静默漏账，也不在导入器重复加钱 |
| 凭证不可变只写禁止修改/删除 | PR03补“封存后不得插入新Entry”和运行角色权限测试 | 借贷仍平衡也不能偷偷扩大旧凭证 |
| 恢复表重复创建、未来模块提前验收 | 固定PR00～PR20依赖与接入归属，允许当前PR修改已有模块完成接线 | 退款通知在PR11接，争议联动在PR13接，L3在PR15扩展已有恢复框架 |
| 运营页面找不到对应接口 | PR16补争议、payout、分润、余额、任务、回补、银行导入与调整创建API | PR17每个页面都能调用已交付接口 |
| 夜间检查、费用预期模型没有实施归属 | 放入PR15，区分PASS/FAIL/INCOMPLETE和UNMODELED_FEE | 缺证据不会显示通过，预期费用不会覆盖实际费用 |
| 文档PR也要求构建，测试发现缺陷却不能修生产代码 | 文档PR检查适用性；核心模型随模块，后期组合测试允许有证据的最小修复 | 减少无意义阻塞，同时保持资金规则与验证结果可追溯 |

## 3. 放进新工程的方式

新仓库建议命名为 `stripe-payment-ledger`；具体磁盘位置在创建工程时确定。将本包六个Markdown文件放在同一个 `docs/product/` 目录，相对链接即可继续使用。之后由PR00创建以下工程级规范，PR01再建运行骨架：

```text
stripe-payment-ledger/
  docs/
    product/                 本文档包
    contracts/               OpenAPI与Provider契约、测试能力矩阵
    state-machines/          支付/操作/退款/争议/payout状态规则
    ledger/                  科目、事件键、分录规则、范围与锁序
    spec/                    需求到验收/PR索引，不复制出第二套相反规则
    adr/                     架构与关键设计选择
  pom.xml                    PR01生成
  mvnw / mvnw.cmd            PR01生成
  src/                       PR01后逐步实现
```

目录是拟建结构，不代表这些文件已经全部生成。工程内部无需保留输入文件原先所在的目录名或路径。

## 4. 开工顺序和阶段门槛

1. **PR00：把首批接口写到可实施。** 请求/响应字段、认证、幂等键范围、状态转换、操作关联、金额边界、分录封存和锁序都要有明确选择。版本与账户能力清单区分待验证和已验证，不以占位文件数量作为完成标准。
2. **PR01～PR05：建立可运行基础并验证真实契约。** 工程骨架、认证隔离、账本、Fake Provider、真实StripeAdapter逐步交付。测试账户阻塞时可以开发独立的Fake部分，但真实Stripe契约门槛保持未通过。
3. **PR06～PR11：完成第一个收退款闭环。** 创建Checkout、完成测试支付、丢失结果后恢复、BT只入账一次、部分退款预占/完成/恢复。操作日志与必要指标跟随模块交付。
4. **PR12～PR17：补齐完整财务与运营。** 分润、争议、payout/模拟银行、独立对账、夜间检查、权限审批和页面。
5. **PR18～PR20：形成可展示证据。** 扩展组合属性测试与故障矩阵、完成本地模拟性能和备份恢复、编写英文演示与有证据的简历材料。

从PR06开始演示支付，不必等待完整后台。基础不变量和并发用例随模块执行；PR18负责组合扩展，不能成为第一次检验资金正确性的时间点。

## 5. 面试材料怎样使用

先练清楚支付超时、退款预占、凭证不可变、BT与银行证据区别，以及独立对账。每完成一个模块，再用该组问题检验自己能否画图、手算和定位到实际代码/实验。

回答采用“问题 → 规则 → 事务或证据 → 失败路径 → 实际验证”的顺序。框架知识用于解释项目取舍，不以堆概念代替结果。手册中的题目是基于项目设计推导的准备方向，不是任何公司的真实面试题库或必问承诺。

尚未完成时，使用“设计上计划这样做”的表述；完成后用自己的实际命令、运行ID、失败seed、提交和报告替换模板。Fake效果、Stripe测试契约、模拟银行证据分别标注，不写成生产业务规模。
